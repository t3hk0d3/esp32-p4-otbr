# ESP32-P4 chip revision 3 builds Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Boards with an ESP32-P4 of chip revision v3.x can install and update this firmware
([issue 53](https://github.com/t3hk0d3/esp32-p4-otbr/issues/53)), and boards below v3 keep working unchanged.

**Architecture:** ESP-IDF v6.1 makes revisions below 3.0 and from 3.0 up mutually exclusive in one image, so each
release carries two P4 builds from the same commit. The existing file names stay the below-v3 build, because boards in
the field download `otbr.bundle` by that name. The v3 build gets a `-rev3` suffix and a v3 board asks for its own
bundle, chosen at compile time. C6 images and the web UI are the same for both.

**Tech Stack:** ESP-IDF v6.1, CMake, bash, Python tools with pytest, Unity host tests, MkDocs, ESP Web Tools 10.4.0.

**Spec:** this plan and issue 53; no separate design doc.

**Styleguide:** `STYLEGUIDE.md` (`make lint`). Host tests are named `"<scenario>: <effect>"`. Routine tasks get a
Makefile target with a `## ` comment. Guides give the release-file way first and `make` as a short note after it.

## Global Constraints

- Below-v3 file names do not change: `otbr.bundle`, `p4-flash.zip`. New files: `otbr-rev3.bundle`, `p4-flash-rev3.zip`.
- v3 overlay `p4/sdkconfig.defaults.rev3`: `CONFIG_ESP32P4_SELECTS_REV_LESS_V3=n`, `CONFIG_ESP32P4_REV_MIN_301=y`.
  This is ESP-IDF's default minimum and what the reporter tested. A v3.0 chip is not supported.
- `p4/sdkconfig.defaults` keeps `CONFIG_ESP32P4_SELECTS_REV_LESS_V3=y`; `make build` stays a below-v3 build.
- `versions.txt` keeps its format, with one `p4 app:` line. Both P4 builds of a release carry the same version string.
- No flashing inside tasks. Host tests and builds only; the on-board pass comes after review and fixes.

## Facts established while planning

- esptool refuses the below-v3 `bootloader.bin` on a v3.2 chip because the image's maximum revision is v1.99.
- A trial build of all projects with the v3 overlay succeeded: images report minimum v3.1 and maximum v3.99, the P4 app
  is 2,658.5 KiB (32.5% of `ota_0`), and the P4 bootloader is 23.5 KiB with 0.5 KiB free. Its `flash_args` says
  `--flash-freq 80m`, where the reporter's below-v3 build says `40m`, so each manifest must come from its own zip.
- ESP Web Tools picks a build by `chipFamily` and `serialType` only, so one manifest cannot tell revisions apart. It
  reads the button's `manifest` when the button is pressed, so a page can set it beforehand.
- esptool-js 0.6.0, which ESP Web Tools uses, ships a browser `bundle.js` and has
  `chip.getChipRevision(loader)` for the P4, returning major * 100 + minor.
- A second `requestPort` needs a fresh user gesture, so detection and install are two presses.
- `esp_ota_end` validates the chip revision of the app image through `esp_image_verify`, before the only commit point
  (`esp_ota_set_boot_partition`). A wrong-revision bundle therefore ends as 400 `invalid_bundle` with the running
  firmware untouched. This comes from reading the source and is confirmed on the board in the hardware pass.
- The bootloader offset is `0x2000` for all P4 revisions.
- The version stamp is the configure time, so two P4 builds would differ. `self_update_compare` would then report a
  v3 board as always older or newer than the release, unless the builds share a stamp.

## Review Focus

1. Docs publish while the latest release has no `p4-flash-rev3.zip` (every master push until the next release): the
   site still publishes and a detected v3 chip is told there is no firmware yet. Test in Task 4.
2. The two P4 builds of a release end up with different versions (a stale configure): packaging fails instead of
   publishing a release that always offers an update. Test in Task 3.
3. A changed `sdkconfig.defaults` with an existing `p4/sdkconfig.rev3`: it is regenerated, as for the other
   sdkconfigs. Test in Task 1.
4. A test build in `p4/build-rev3` reaching a release: packaging refuses it. Test in Task 3.
5. A below-v3 board on a released firmware reads the new release: same `versions.txt`, same `otbr.bundle` URL. Test in
   Tasks 2 and 3.

## BDD skeleton

```
tools/version.cmake
    PROJECT_VER
        With OTBR_BUILD_STAMP set
            - uses that stamp in place of the current time
        Without OTBR_BUILD_STAMP
            - uses the configure time, as before

tools/build_all.sh
    (no variant option)
        On a normal run
            - builds p4 into p4/build from sdkconfig.defaults into p4/sdkconfig
    --rev3
        On a normal run
            - builds p4 into p4/build-rev3 from sdkconfig.defaults plus sdkconfig.defaults.rev3 into p4/sdkconfig.rev3
            - builds the C6 projects once, as before
        With --test
            - adds sdkconfig.defaults.test, into p4/sdkconfig.rev3.test
        With a defaults file newer than p4/sdkconfig.rev3
            - deletes p4/sdkconfig.rev3 first
    --all-p4
        On a normal run
            - builds both P4 variants
            - passes the same OTBR_BUILD_STAMP to both
        With --rev3 as well
            - exits 2 with the usage line

self_update_bundle_name(bool rev3)
    For a below-v3 build
        - returns "otbr.bundle"
    For a v3 build
        - returns "otbr-rev3.bundle"

device_api update_bundle
    On a v3 build
        - downloads <release>/otbr-rev3.bundle
    On a below-v3 build
        - downloads <release>/otbr.bundle

tools/package_release.sh
    With both P4 builds
        - writes otbr.bundle and p4-flash.zip from p4/build
        - writes otbr-rev3.bundle and p4-flash-rev3.zip from p4/build-rev3
        - lists the new files in SHA256SUMS
        - writes one "p4 app:" line to versions.txt
    With p4/build-rev3 missing
        - exits 1, saying to run make build-release
    With p4/build-rev3 a test build
        - exits 1
    With different versions in the two builds
        - exits 1, naming both versions

make docs-firmware
    With a release that has both zips
        - unpacks them to firmware/ and firmware/rev3/, each with a manifest.json
    With a release that has no p4-flash-rev3.zip
        - succeeds with firmware/ only

docs/assets/flash_detect.js
    manifestForRevision(revision)
        With a revision of 0 to 199
            - returns "../firmware/manifest.json"
        With a revision of 301 to 399
            - returns "../firmware/rev3/manifest.json"
        With a revision of 200 to 300, or above 399
            - returns null
    detect (the Detect board button)
        On a chip below v3
            - shows the revision and the firmware picked
            - sets the install button's manifest to the below-v3 manifest and shows the button
            - resets the board and releases the serial port
        On a v3.1 or later chip
            - sets the install button's manifest to the rev 3 manifest and shows the button
        On a v3 chip with no rev 3 manifest on the site
            - says this release has no firmware for the chip and keeps the install button hidden
        On a revision no build supports
            - names the revision and keeps the install button hidden
        On a chip that is not an ESP32-P4
            - says so and keeps the install button hidden
        When the port picker is cancelled
            - changes nothing
        When the connection fails
            - says to hold BOOT and try again, or to choose the firmware by hand
            - releases the serial port
    choose by hand
        On picking a revision
            - sets the install button's manifest to that build and shows the button
```

## Hardware pass (after review and fixes, one lean pass)

Lease `p4-otbr-boards/p4-otbr-a` through `clerk` first and re-read `app.version` before each on-board action.

- Below-v3 board, `p4/build` image: boots, and joins or forms on Thread channel 26.
- Below-v3 board: upload `otbr-rev3.bundle`. Expected: 400 `invalid_bundle`, no reboot, running firmware unchanged.
- Below-v3 board, from Chrome on a preview of the site: **Detect board** shows v1.3, picks the below-v3 manifest, and
  the board restarts into its firmware. Stop before **Install**, so no flash write is spent.

**Not coverable on our bench:** no v3 chip is available. Booting, Ethernet, the SPI link to the C6, PSRAM execution and
USB host on v3 stay unverified until someone with a v3 board tries it. The reporter of issue 53 has one; asking them
means a GitHub comment, whose text needs approval first.

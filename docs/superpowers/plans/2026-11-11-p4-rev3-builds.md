# Firmware targets by board and chip Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Boards with an ESP32-P4 of chip revision v3.x can install and update this firmware
([issue 53](https://github.com/t3hk0d3/esp32-p4-otbr/issues/53)), through a target model that can take more boards and
chip revisions later.

**Architecture:** A firmware **target** is a pair of two independent ids: `board_id` (the PCB: pins, flash size) and
`chip_id` (the silicon family, which ESP-IDF builds exclusively). One registry lists the boards, the chips and the
pairs that are built. Each target gets its own sdkconfig from the common defaults plus one overlay per axis, and its
own release files. A board knows its target at compile time and downloads its own bundle.

**Tech Stack:** ESP-IDF v6.1, CMake, bash, Python tools with pytest, Unity host tests, MkDocs, esptool-js 0.6.0
(replaces ESP Web Tools), spark-md5 3.0.2.

**Spec:** this plan and issue 53; no separate design doc. Flasher look and flow:
[Web Flasher Sketch](https://claude.ai/artifact/1Noj29BDdcHaZwbYpCohcu).

**Styleguide:** `STYLEGUIDE.md` (`make lint`). Host tests are named `"<scenario>: <effect>"`. Routine tasks get a
Makefile target with a `## ` comment. Guides give the release-file way first and `make` as a short note after it.

## Global Constraints

- `board_id`: `ESP32-P4-WIFI6-POE-ETH`. `chip_id`: `ESP32-P4-rev1.3` and `ESP32-P4-rev3.0`. Ids never contain `_`.
- Chip revision ranges, as ESP-IDF's revision numbers (major * 100 + minor): `ESP32-P4-rev1.3` is 0 to 199,
  `ESP32-P4-rev3.0` is 301 to 399.
- `ESP32-P4-rev3.0` overlay: `CONFIG_ESP32P4_SELECTS_REV_LESS_V3=n`, `CONFIG_ESP32P4_REV_MIN_301=y` (ESP-IDF's default
  minimum and what the reporter tested). `ESP32-P4-rev1.3` overlay: `CONFIG_ESP32P4_SELECTS_REV_LESS_V3=y`.
- Default target: `ESP32-P4-WIFI6-POE-ETH` with `ESP32-P4-rev1.3`. It builds into `p4/build` and `p4/sdkconfig`, as now.
- Release file names: `<board_id>_<chip_id>.ota` (the OTA bundle, same format as `otbr.bundle`) and
  `full_<board_id>_<chip_id>.zip` (the full USB flash, same contents as `p4-flash.zip`).
- `otbr.bundle` and `p4-flash.zip` stay in every release as copies of the default target: released firmware downloads
  `otbr.bundle` by that name.
- `versions.txt` keeps its format, with one `p4 app:` line. All P4 builds of a release carry the same version string.
- `BOARD` in the Makefile stays the board's network address. The new variables are `BOARD_ID` and `CHIP_ID`.
- No flashing inside tasks. Host tests and builds only; the on-board pass comes after review and fixes.

## Out of scope until a second board exists

- Moving the pins out of `p4/main/board.h` and `common/c6_board/c6_board.h` into per-board files. There is nothing to
  select between yet.
- Building the C6 projects per board. They do not depend on the P4 chip, so one build serves all targets of this board.
- A `board_id` check inside the bundle. Today a wrong-chip bundle is already refused and a wrong-board one cannot
  exist. The second board's plan must add it: two boards with the same chip would pass the revision check.

## Facts established while planning

- esptool refuses the below-v3 `bootloader.bin` on a v3.2 chip because the image's maximum revision is v1.99.
- A trial build of all projects with the v3 settings succeeded: images report minimum v3.1 and maximum v3.99, the P4 app
  is 2,658.5 KiB (32.5% of `ota_0`), and the P4 bootloader is 23.5 KiB with 0.5 KiB free. Its `flash_args` says
  `--flash-freq 80m`, where the reporter's below-v3 build says `40m`, so each manifest must come from its own zip.
- ESP Web Tools picks a build by `chipFamily` and `serialType` only, and shows its own dialog over the page, so the
  flasher uses esptool-js directly.
- esptool-js 0.6.0 ships a browser `bundle.js`, has `chip.getChipRevision(loader)` for the P4, and has `writeFlash` with
  `reportProgress(fileIndex, written, total)`, `eraseAll` and an optional `calculateMD5Hash`. Browsers have no built-in
  MD5, hence spark-md5. The port stays open from detection to install, so there is one port prompt. The chip can be
  read; the board cannot.
- `esp_ota_end` validates the chip revision of the app image through `esp_image_verify`, before the only commit point
  (`esp_ota_set_boot_partition`). A wrong-chip bundle therefore ends as 400 `invalid_bundle` with the running firmware
  untouched. This comes from reading the source and is confirmed on the board in the hardware pass.
- The bootloader offset is `0x2000` for all P4 revisions.
- The version stamp is the configure time, so builds would differ, and `self_update_compare` would report a board as
  always older or newer than the release unless the builds share a stamp.
- The longest asset URL is about 145 characters, within `URL_MAX` (192 and 256).

## Review Focus

1. Docs publish while the latest release predates targets (every master push until the next release): the site still
   publishes the default target from `p4-flash.zip`, and a detected v3 chip is told there is no firmware yet. Test in
   Task 4.
2. The P4 builds of a release end up with different versions (a stale configure): packaging fails instead of publishing
   a release that always offers an update. Test in Task 3.
3. A chip overlay and the registry's revision range disagree: packaging fails, since the flasher would pick an image
   that does not boot. Test in Task 3.
4. Moving options into overlays changes the default build by accident: the default target's sdkconfig stays the same.
   Checked in Task 1.
5. A board on a master build presses "Install the latest release anyway" before the first release with targets: the
   target-named file is missing, so it fails as `transfer_failed` and the running firmware stays. Test in Task 2.

## BDD skeleton

```
tools/targets.py
    resolve(board_id, chip_id)
        With the default target
            - returns build dir p4/build, sdkconfig p4/sdkconfig
        With another target
            - returns build dir p4/build_<board_id>_<chip_id>, sdkconfig p4/sdkconfig_<board_id>_<chip_id>
        On every target
            - returns defaults: sdkconfig.defaults, the board overlay, the chip overlay, in that order
        With an unknown board or chip
            - exits 2, listing the known ids
        With a known board and chip that are not a listed pair
            - exits 2, listing the targets
    load
        With an id containing "_"
            - fails, naming the id

tools/version.cmake
    PROJECT_VER
        With OTBR_BUILD_STAMP set
            - uses that stamp in place of the current time
        Without OTBR_BUILD_STAMP
            - uses the configure time, as before

tools/target.cmake
    With OTBR_BOARD_ID and OTBR_CHIP_ID set
        - defines both as C string macros for all components
    With either missing
        - fails the configure step

tools/build_all.sh
    (no target option)
        On a normal run
            - builds the default target
    --target <board_id>/<chip_id>
        On a normal run
            - builds p4 with that target's build dir, sdkconfig, defaults and ids
            - builds the C6 projects once
        With --test
            - appends sdkconfig.defaults.test and uses <sdkconfig>.test
        With a defaults file newer than the sdkconfig
            - deletes the sdkconfig first
    --all-targets
        On a normal run
            - builds every target with the same OTBR_BUILD_STAMP
        With --target as well
            - exits 2 with the usage line

self_update_bundle_name(board_id, chip_id, out, cap)
    With valid ids
        - writes <board_id>_<chip_id>.ota and returns ESP_OK
    With a buffer too small
        - returns ESP_ERR_INVALID_SIZE and leaves an empty string

device_api update_bundle
    On any target
        - downloads <release>/<board_id>_<chip_id>.ota
    With the file missing from the release
        - answers transfer_failed naming the URL, nothing committed

GET /device/update
    On any target
        - includes board_id, chip_id and bundle (the file name)

firmware page
    With an update state
        - names that bundle file in the upload box

tools/package_release.sh
    With every target built
        - writes the bundle and zip of each target
        - writes otbr.bundle and p4-flash.zip identical to the default target's
        - lists all of them in SHA256SUMS
        - writes one "p4 app:" line to versions.txt
    With a target's build dir missing
        - exits 1, saying to run make build-release
    With a target that is a test build
        - exits 1
    With different versions between targets
        - exits 1, naming them
    With a sdkconfig whose revision range differs from the registry
        - exits 1, naming the target

make docs-firmware
    With a release that has target zips
        - unpacks each to firmware/<board_id>/<chip_id>/ with a manifest.json
        - writes firmware/targets.json listing those targets, their revision ranges and manifest paths
    With a release that has only p4-flash.zip
        - publishes it as the default target

docs/assets/flasher.js
    targetsForRevision(targets, revision)
        With a revision inside a target's range
            - returns the targets of that chip
        With a revision no target covers
            - returns an empty list
    detect (the Detect board button)
        With one board for the detected chip
            - shows the chip, board and release, and offers Install
            - keeps the serial port open
        With several boards for the detected chip
            - asks which board, and offers Install once one is picked
        With a revision no published target covers
            - names the revision, offers no Install, resets the board and releases the port
        On a chip that is not an ESP32-P4
            - says so, offers no Install, resets the board and releases the port
        When the port picker is cancelled
            - changes nothing
        When the connection fails
            - says to hold BOOT, press RESET and try again, or to choose by hand
            - releases the serial port
    choose by hand
        On picking a board and chip, then Install
            - asks for the port and writes that target without reading the revision
    install
        On success
            - writes each part of the target's manifest at its offset, keeping its flash settings
            - verifies each part by MD5
            - shows overall progress and which part is being written
            - resets the board and releases the port
            - links to the board's page
        With erase chosen
            - erases the whole flash before writing
        With erase not chosen
            - does not erase
        When an image fails to download
            - stops before touching the flash and says which file
        When the write or the MD5 check fails, or the cable is pulled
            - says the board may not start and offers to install again
            - releases the port
        While writing
            - warns before the tab is closed
    In a browser without Web Serial
        - says to open the page in Chrome or Edge on a desktop and offers no Detect board
```

## Hardware pass (after review and fixes, one lean pass)

Lease `p4-otbr-boards/p4-otbr-a` through `clerk` first and re-read `app.version` before each on-board action.

- `ESP32-P4-rev1.3` board, default target: boots, and joins or forms on Thread channel 26. `GET /device/update` shows
  its ids and bundle name.
- Same board: upload the `ESP32-P4-rev3.0` bundle. Expected: 400 `invalid_bundle`, no reboot, running firmware unchanged.
- Same board, from Chrome on a preview of the site, by you at the bench: **Detect board** shows v1.3 and picks the
  default target. **Install** without erase writes it, the MD5 checks pass, and the board restarts on it with its stored
  network intact. This is the one flash write of the pass, and it is needed now that the page owns the flashing.
- Same page: pull the cable during a second **Install**, only if a further write is acceptable. Expected: the failure
  message, the port released, and a following **Install** succeeds.

**Not coverable on our bench:** no v3 chip is available. Booting, Ethernet, the SPI link to the C6, PSRAM execution and
USB host on v3 stay unverified until someone with a v3 board tries it. The reporter of issue 53 has one; asking them
means a GitHub comment, whose text needs approval first.

# ESP32-P4 OpenThread Border Router — Design Spec

- **Date:** 2026-10-30
- **Board:** Waveshare ESP32-P4-WIFI6-POE-ETH (SKU 32832) — https://docs.waveshare.com/ESP32-P4-WIFI6-POE-ETH
- **Status:** Approved design, updated with Phase 0 hardware results (`docs/phase0/RESULTS.md`)

### Change log

- **2026-10-31 — R14: RCP firmware decoupled from P4 image.** The C6 RCP firmware (`c6_rcp`
  app `.bin`) is a standalone release artifact, distributed and updated separately from the P4
  firmware. No RCP image is stored on the P4 (`rcp_0`/`rcp_1` partitions removed), no expected RCP
  version, no automatic push at boot, no `esp_rcp_update` dependency, no slot pinning. The RCP is
  updated by streaming it through `POST /device/radio/firmware` (upload) or
  `POST /device/radio/firmware?from_url=<url>` straight into the C6 updater. The OTA bundle carries web
  assets and the P4 app only. The frozen C6 base image (bootloader, partition table, updater) is not
  RCP firmware and stays embedded in the P4 app.

## 1. Goal

A standalone Thread Border Router running on the Waveshare ESP32-P4-WIFI6-POE-ETH board, with
Ethernet (PoE) as the backbone and the on-board ESP32-C6 as the 802.15.4 radio co-processor (RCP),
reached over the existing P4↔C6 SDIO traces used as SPI. No board modifications or permanent wiring.

### In scope (MVP)

1. Thread Border Router on Ethernet: bidirectional IPv6 routing, NAT64, SRP server / service
   discovery, multicast forwarding, Border Agent (`_meshcop._udp`) — as provided by ESP-IDF's
   OpenThread border-router libraries.
2. DHCPv6 Prefix Delegation for the OMR prefix, always enabled; falls back to the local ULA OMR
   prefix when no delegating router exists.
3. Upstream esp-thread-br Web GUI and REST API, kept compatible with the ot-br-posix REST API that
   Home Assistant's `otbr` integration (`python-otbr-api`) uses.
4. Runtime switch between **Border Router mode** and **Sniffer mode** from the Web UI / API, with
   a pcap stream consumable by Wireshark. No reflashing.
5. OTA update of the P4 (upload over HTTP, and URL pull), shipping P4 firmware and Web UI assets
   together as one paired set with rollback.
6. In-band update of the C6 RCP firmware over SPI, driven by the P4 on request (upload or URL,
   streamed straight through, nothing stored on the P4), with a frozen C6 updater app so the C6
   cannot be bricked by a bad RCP image. The RCP firmware is a separate release artifact with its
   own lifecycle (R14).
7. Optional **maintenance jumper** (three wires from the P4 40-pin header to the C6's H7 header):
   when present, the P4 can drive the C6 ROM bootloader to do the first-time C6 install (no external
   USB-UART adapter), full C6 recovery, field updates of the C6 base image (bootloader, partition
   table, updater), and C6 console capture. Without the jumper everything else works unchanged.
8. Deterministic core scheduling (core 0 = network, core 1 = management) and a diagnostics API with
   per-core and per-task CPU metrics, memory and OpenThread lock statistics.
9. Ethernet **VLAN support** with two network modes: `single` (one interface, tagged or untagged,
   carrying everything — the default) and `split` (management and Thread backbone on separate
   VLAN interfaces, strictly isolated, no routing between them). Configured at runtime with a
   confirm-or-revert safety net (§5.13).

### Non-goals (MVP)

- Authentication of the Web UI / REST / device API. The LAN is trusted. (Endpoint layout must allow
  adding auth later without changing paths.)
- ESPHome native API; MQTT.
- Wi-Fi / BLE (the C6 is a dedicated 802.15.4 radio).
- Sniffing while the Border Router runs (single radio; OpenThread forbids promiscuous mode while
  the Thread netif is up).
- Re-partitioning flash on the fly (the layout permits it later; not implemented).
- Auto-forming a Thread network when no dataset is stored.
- Updating the C6 base image (bootloader, partition table, updater app) in the field **without** the
  maintenance jumper.
- Bundling the RCP firmware with the P4 firmware, storing it on the P4, or tracking an "expected" RCP
  version on the P4 (R14); automatic RCP updates.
- Spinel over UART (the jumper is a maintenance link only; spinel stays on SPI).
- Routing between the management VLAN and the Thread backbone VLAN (explicitly prevented).
- More than two VLANs / Ethernet interfaces (exactly one management and one Thread interface at most);
  802.1p priority tagging.

## 2. Hardware facts

Extracted from the board schematic (`docs/hardware/ESP32-P4-WIFI6-POE-ETH-Schematic.pdf`).

### 2.1 Ethernet (IP101GRI, internal EMAC, RMII)

| Signal | P4 GPIO |
|---|---|
| MDC | 31 |
| MDIO | 52 |
| PHY reset | 51 |
| TX_EN | 49 |
| TXD0 / TXD1 | 34 / 35 |
| CRS_DV | 28 |
| RXD0 / RXD1 | 29 / 30 |
| RMII 50 MHz REF_CLK **input** (generated by the PHY from its 25 MHz crystal) | 50 |
| PHY address | 1 (AD0 pulled up via R75, AD3 pulled down via R72) |

The RJ45 (HBJ-6117ANL) has PoE center taps; PoE needs the optional PoE module.

### 2.2 P4 ↔ C6

The C6 module's UART0 TX/RX and IO9 (BOOT strap) are routed **only** to the 4-pin header H7
(`C6_U0TXD, C6_U0RXD, GND, C6_IO9`), not to the P4. The P4 therefore cannot put the C6 into ROM
download mode; upstream's UART-based RCP updater cannot be used.

| Role in this design | P4 GPIO | C6 pin | Original SDIO role |
|---|---|---|---|
| SPI SCLK | 18 | IO19 | CLK |
| SPI MOSI (P4→C6) | 19 | IO18 | CMD |
| SPI MISO (C6→P4) | 14 | IO20 | D0 |
| SPI CS | 15 | IO21 | D1 |
| INT (C6→P4, active low) | 16 | IO22 | D2 |
| spare | 17 | IO23 | D3 |
| UPDATE select (P4→C6; low at reset = boot updater) | 6 (via R52, 0 Ω) | IO2 | — |
| RESET (C6 CHIP_PU) | 54 (via R54, 0 Ω) | EN | — |

All six SDIO lines have 51 kΩ pull-ups to 3V3. P4 GPIO6 idles high (driven) except while selecting
the updater.

**Optional maintenance jumper** (P4 40-pin header → H7, SH1.0 1 mm pitch connector):

| Role | P4 GPIO | H7 pin | C6 pin |
|---|---|---|---|
| UART RX (C6 console / ROM loader → P4) | 4 (`JUMPER_RX`), header pin 18 | 1 `C6_U0TXD` | U0TXD |
| UART TX (P4 → C6, ROM loader only) | 5 (`JUMPER_TX`), header pin 16 | 2 `C6_U0RXD` | U0RXD |
| ground | GND, header pin 14 | 3 | GND |
| BOOT strap (low at reset = ROM download) | 22 (`JUMPER_BOOT`), header pin 12 | 4 `C6_IO9` | IO9 |

Verified in Phase 0 (detection, ROM connect, write/verify at 1.5 Mbaud). GPIO4/5 match Espressif's
P4 reference wiring. Header pins to leave free: 15 (GPIO6) and 32 (GPIO54) — already wired to the
C6 on the board; 3/5 (GPIO7/8, codec I2C); 8/10 (GPIO37/38, P4 console); 22/23 (GPIO1/0, 32 kHz
crystal); 24 (GPIO36, strap); 27/28 (GPIO24/25, USB); 35 (GPIO53, speaker amp); 40 (GPIO45).
Electrical rules: `JUMPER_BOOT` is
high-impedance except during ROM download (IO9 has an internal pull-up); `JUMPER_TX` is idle
(high-impedance or idle-high) outside ROM download so nothing is injected into the C6 console;
C6 IO8 is already pulled up (R25, 10 kΩ), as ROM download requires.

### 2.3 Other facts

- P4: ESP32-P4NRW32X **chip revision v1.3**, 32 MB PSRAM (AP, 200 MHz), 32 MB NOR flash
  (GigaDevice). ESP-IDF v6.1 targets rev ≥ v3.1 by default: every P4 build sets
  `CONFIG_ESP32P4_SELECTS_REV_LESS_V3=y`.
- C6 module: **8 MiB flash** (measured; the schematic's "MINI-1-N4" label is wrong), chip revision
  v0.2. The C6 layout below is 4 MB-safe and leaves room to grow the slots.
- The C6 module uses an external antenna (IPEX). **An antenna must be attached.**
- C6 console (UART0) is only reachable on H7. First-time C6 install:
  - **with the maintenance jumper:** flash only the P4 over its USB-C port; on first boot the P4
    installs the complete C6 image via ROM download (§5.10). The C6's factory ESP-Hosted firmware is
    overwritten;
  - **without the jumper:** a 3.3 V USB-UART adapter on H7 with IO9 tied to GND at reset.

## 4. C6 side

### 4.1 C6 flash layout (4 MB-safe)

| Partition | Type/subtype | Size | Content |
|---|---|---|---|
| bootloader | — | stock | stock bootloader, `CONFIG_BOOTLOADER_APP_TEST=y`, test pin IO2, active low, `CONFIG_BOOTLOADER_HOLD_TIME_GPIO=0` |
| partition table | — | — | |
| `nvs` | data/nvs | 24 KB | |
| `otadata` | data/ota | 8 KB | |
| `test` | app/test | 512 KB | `c6_updater` (frozen) |
| `ota_0` | app/ota_0 | 1.5 MB | `c6_rcp` slot A |
| `ota_1` | app/ota_1 | 1.5 MB | `c6_rcp` slot B |

No C6 bootloader app-rollback. The P4 does not track which RCP version should run (R14); the RCP
firmware is pushed on request, `END` is the only boot-slot switch, and OpenThread's own RCP
compatibility check is the compatibility gate at boot.
Explicit offsets (validated): `nvs` 0x9000, `otadata` 0xf000, `test` 0x20000, `ota_0` 0xa0000,
`ota_1` 0x220000. The bootloader samples IO2 ~88 ms after reset release, so the P4 keeps GPIO6 low
for the whole updater session (holding it 5–50 ms is not enough).

### 4.2 `c6_rcp`

- ESP-IDF `examples/openthread/ot_rcp` configured for `CONFIG_OPENTHREAD_RCP_SPI` on the pins in
  §2.2 (set in the example's `main/esp_ot_config.h`: MOSI IO18, MISO IO20, SCLK IO19, CS IO21,
  `intr_pin` IO22); no other source changes for the MVP. Image ≈ 272 KB.
- Release artifact: the plain app image `c6_rcp.bin` (the ESP-IDF app `.bin`, ≈ 272 KB), uploaded
  as-is through `/device/radio/firmware` (§5.6.1). No packager, no `rcp_version` file and no subfile
  container are involved (R14). The version the updater reports is the app descriptor's `version`,
  stamped from `PROJECT_VER`.
- `PROJECT_VER` = `<UTC build timestamp YYYYMMDDTHHMMSSZ>-<7-hex git hash>[-dirty]` (≤ 30 chars;
  `esp_app_desc_t.version` holds at most 31), set by the build. The P4 app and `c6_rcp` use this format
  (the frozen updater does not: §4.3). The P4 only displays the RCP version; it never compares it with an
  expectation.
- Console on UART0 (H7).

### 4.3 `c6_updater`

- Runs when IO2 is held low at reset (bootloader APP_TEST). SPI slave on the same pins and INT line;
  no OpenThread, no Wi-Fi.
- `PROJECT_VER` is **content-addressed**, `base-<8 hex>` (`tools/base_version.cmake`): a SHA-1 over
  `c6_updater/main/*`, `common/rcp_sync_proto/*`, `common/c6_board/*` (without host tests and build output),
  `c6_updater/sdkconfig.defaults` and the IDF version, independent of the build time and of git. This one
  string versions the whole **C6 base image** (bootloader + partition table + updater), which is only ever
  written together; the P4 embeds the same string, so an ordinary P4 release does not trigger a ROM
  recovery.
- Reports versions of the **boot slot** (the slot the C6 bootloader boots: the one `otadata` selects when
  it holds a valid image, otherwise the first valid slot, `ota_0` then `ota_1`, which is what happens
  after a ROM recovery erased `otadata`) and the **other slot**. A slot
  reports a version only if ESP-IDF image verification passes; otherwise it reports empty.
- Writes only the **inactive** slot; switches the boot slot only after the new image verifies (`END`
  is the only boot-slot switch, so an aborted transfer leaves the previous firmware booting).

### 4.4 Updater wire protocol (`common/rcp_sync_proto`)

P4 is SPI master. All integers little-endian.

**Frame:** `magic u16 | type u8 | seq u8 | len u16 | payload[len ≤ 4096] | crc32 u32`
(CRC-32 over header and payload).

**Handshake:** the C6 queues its receive buffer and pulls INT low ("ready for request"); the P4
sends a request frame; the C6 processes it, queues the reply, pulls INT low ("reply ready"); the P4
clocks out the reply.

| Request | Payload | Reply |
|---|---|---|
| `HELLO` | — | `proto_version u16, updater_version str, boot_slot_version str, other_slot_version str, slot_size u32` |
| `BEGIN` | `image_size u32` | `OK` / `ERR(code)` — erases the inactive slot; P4 timeout 30 s |
| `DATA` | `offset u32, bytes[]` | `OK(next_offset)` / `ERR(expected_offset)` — sequential writes only |
| `END` | — | `OK` / `ERR(code)` — verifies image, switches boot slot to it |

- Bad CRC → `NAK`; the P4 resends the same `seq`.
- A repeated `seq` returns the cached reply (retransmits are idempotent).
- No reboot command; the P4 resets the C6 via GPIO54.
- `BEGIN` carries the total image size, so a push needs the size up front (`Content-Length` for
  uploads and URL pulls; chunked uploads without a length are rejected with 400).
- SPI clock 10 MHz, mode 0, for both the updater protocol and spinel (Phase 0: clean at 10/20/40 MHz;
  10 MHz keeps 4× margin, which matters because spinel-over-SPI frames carry no CRC).

## 5. P4 side

### 5.1 P4 flash layout (32 MB)

Fixed data first, firmware slots at the end, free space at the very end so slots can be grown later
without touching fixed data.

| Partition | Type/subtype | Size | Notes |
|---|---|---|---|
| `nvs` | data/nvs | 64 KB | Thread dataset (OpenThread settings), device settings (namespace `otbr_dev`) |
| `otadata` | data/ota | 8 KB | |
| `coredump` | data/coredump | 128 KB | |
| *(reserved)* | — | up to the 1 MB mark | room for future fixed data |
| `ota_0` | app/ota_0 | 8 MB | P4 app, slot A |
| `ota_1` | app/ota_1 | 8 MB | P4 app, slot B |
| `web_0` | data/spiffs | 2 MB | Web UI assets paired with `ota_0` |
| `web_1` | data/spiffs | 2 MB | Web UI assets paired with `ota_1` |
| *(free)* | — | ~11 MB | resizable bottom area (grew by the former `rcp_0`/`rcp_1` 4 MB, R14) |

**Pairing invariant:** the running `ota_N` always uses `web_N`. Updates write the inactive pair
`(ota_M, web_M)`; `esp_ota_set_boot_partition(ota_M)` is the only commit point. Bootloader rollback
therefore restores a consistent pair automatically. No RCP image is stored on the P4 (R14); the C6
holds its own firmware in its own flash.

First install over USB flashes `ota_0` and `web_0`; the `_1` slots are filled by the first OTA.
Partitions placed before the free area keep their offsets, so a device flashed with the older
layout (with `rcp_*`) needs a one-time USB reflash of the partition table (no field devices exist
yet).

### 5.2 *(removed in R14)*

Removed in R14: RCP firmware is distributed and updated separately; no slot pinning, no RCP image
storage on the P4. (Section number kept so references stay stable.)

### 5.3 Boot sequence

1. Bootloader starts `ota_N` (pending-verify if freshly updated).
2. NVS, event loop. **Network** (`netcfg`, §5.13): load the network config (or the pending trial
   config), create the interface(s) — `single`: one interface; `split`: `mgmt` and `thread_bb` —
   each with DHCPv4 or static IPv4 and IPv6 link-local + SLAAC. Mount the active `web_N` at `/web`.
3. **Radio probe** (`rcp_sync_probe`, best effort; there is no radio sync and no push at boot):
   1. Drive GPIO6 low, pulse GPIO54 → C6 boots `c6_updater`. While pulsing, listen on `JUMPER_RX`
      at 115200 baud: seeing the C6 ROM boot banner means the maintenance jumper is present
      (passive detection, no extra boot time).
   2. `HELLO`. If the jumper is present and the updater does not answer after the normal retries,
      or `updater_version` differs from the embedded C6 base image version → **ROM recovery**
      (§5.10), then restart this step. Without the jumper an unreachable or different updater is
      only recorded in status.
   3. Record `boot_slot_version` as the installed RCP version for `/device/status` (empty = no valid
      RCP firmware). No comparison with any expected version.
   4. Release the SPI bus completely. A failed probe (no answer, bad frame) must not block boot: the
      installed version is then "unknown" and boot continues with step 4.
4. Drive GPIO6 high, pulse GPIO54 → C6 boots its boot slot (always a hardware reset before spinel
   init: Phase 0 saw the first boot after flashing the P4 fail its spinel reset when the C6 SPI
   slave was left mid-frame). Register `esp_openthread_register_rcp_failure_handler()` **before**
   `esp_openthread_init()` — without it a failed RCP reset asserts and reboots. Start OpenThread
   with `RADIO_MODE_SPI_RCP` on the §2.2 pins at 10 MHz.
   - If the probe reported an empty installed version (no valid RCP firmware) → skip OpenThread and
     enter `RADIO_FAULT` with reason `"no rcp firmware"`.
   - If OpenThread rejects the RCP (compatibility check or reset failure → RCP failure handler) →
     `RADIO_FAULT` with reason `"rcp incompatible"`. `/device/status` `rcp.compatible` is `false`.
   - Recovery from either reason is uploading RCP firmware through `/device/radio/firmware` (upload, or `?from_url=`)
     (§5.6.1); the HTTP server is up in every mode.
5. When the backbone interface (`thread_bb` in split mode, the single interface otherwise) has an
   address: `esp_openthread_set_backbone_netif()` with that interface,
   `esp_openthread_border_router_init()`, enable DHCPv6-PD
   (`otBorderRoutingDhcp6PdSetEnabled(true)`). If an active dataset is stored, start Thread with it;
   otherwise stay idle until a dataset is set via Web UI / REST.
6. Start mDNS (hostname `esp-otbr-<last 3 MAC bytes>`, announced and answered on the one mDNS
   interface only: the single interface in single mode, `thread_bb` in split mode, never `mgmt`; OpenThread's services — Border
   Agent, SRP advertising proxy — on the same interface) and the HTTP server with `esp_br_web_start("/web")`, then register
   `/device/*`. The HTTP server starts in every mode, including `RADIO_FAULT`; per-interface
   service policy (§5.13) is enforced per request.
7. **App validity:** if the image is pending-verify, mark it valid once startup is complete, the HTTP
   server is listening, and the app has run 60 s without reset. Radio state, Ethernet link, probe
   result and OpenThread state are deliberately **not** criteria. There is no self-reboot timer;
   any reset before marking (panic, watchdog, brownout) makes the bootloader roll back.

### 5.4 Mode manager (`br_core`)

Single owner of mode transitions; all OpenThread calls under the OpenThread lock.

```
            sniff(channel)            stop / duration elapsed / client gone
BR_RUNNING ───────────────▶ SNIFFER ─────────────────────────▶ BR_RUNNING

BR_RUNNING or SNIFFER ── RCP failure ──▶ RADIO_FAULT ── recovered ──▶ BR_RUNNING
```

States: `STARTING`, `BR_RUNNING` (includes "idle, no dataset"), `SNIFFER`, `RADIO_FAULT`.

- **BR → SNIFFER:** Thread stop, OpenThread IPv6 netif down (required by OpenThread for raw link /
  promiscuous), raw link receive enabled (`otLinkRawSetReceiveDone`), **then** set the channel and
  promiscuous mode through the raw link. **Ethernet IPv4/IPv6 stay up.**
  Never call `otLinkSetChannel()` while the raw link is disabled: with Thread stopped it
  **invalidates the active and pending datasets** (Phase 0 finding); with the raw link enabled it
  only sets the raw-link channel.
- **SNIFFER → BR:** raw link off, OpenThread netif up, Thread start; the active dataset (and its
  channel) is untouched, which `br_core` verifies by comparing the active dataset TLVs before and
  after. Phase 0: 20/20 cycles, rejoin ≈ 1.4 s. If restore fails → reboot (sniffer mode is never persisted, so the device comes back
  as BR).
- **RADIO_FAULT recovery ladder:** (1) reset C6 via GPIO54 and restart OpenThread, (2) stay in fault. At most
  3 automatic recoveries per 10 minutes; afterwards only a firmware upload (§5.6.1) or reboot. A
  fault with reason `"no rcp firmware"` is not retried automatically.
  Rationale: a "resync" no longer exists, so there is nothing to re-push on its own.
- `br_core_thread_ops_allowed()` exposes the mode to the REST guard.

### 5.5 Sniffer

- Requires `OPENTHREAD_CONFIG_LINK_RAW_ENABLE 1` in an OpenThread custom header
  (`CONFIG_OPENTHREAD_HEADER_CUSTOM=y`); OpenThread core is compiled from source, so this works with
  the BR build (validated in Phase 0).
- Receive callback runs in the OpenThread task and only copies frame, timestamp, RSSI, LQI into a
  256 KB PSRAM ring buffer; overflow drops frames and increments a counter.
- Output: pcap, link type 283 (`LINKTYPE_IEEE802_15_4_TAP`) with FCS type, channel, RSSI, LQI TLVs. The capture carries
  **no FCS**: the radio checks the FCS itself and the ESP 802.15.4 driver replaces the last two bytes of the delivered
  PSDU with RSSI and LQI. The sniffer strips them and the TAP FCS type TLV is 0 (none); RSSI and LQI come from the TLVs
  (`SNIFFER_RX_PSDU_HAS_FCS false`, found on the board with Wireshark).
- One capture at a time; served from an async HTTP handler with its own worker task.

### 5.6 OTA bundle and update path

**Bundle format** (produced by `tools/`):

```
[ ota_bundle header ][ web SPIFFS image (trailing 0xFF trimmed) ][ P4 app image ]
header = magic u32 | format_version u16 | reserved u16 | web_len u32 | web_sha256[32]
```

The payload after the web image is the plain P4 app image (`p4.bin`); there are no RCP subfiles and
no upstream combined-image container (R14). `tools/make_bundle.py` builds the bundle from the web
image and `p4.bin` only.

**`esp_br_http_ota` patch:** split into a source-agnostic streaming core plus two entry points:
URL pull (existing `esp_http_client` behaviour) and HTTP upload (fed by `httpd_req_recv`). The core:

1. Parses the bundle header.
2. Erases the inactive `web_M` partition (unmounted) and writes the web image raw; verifies SHA-256.
3. Writes the remainder to `ota_M` via `esp_ota_*` (the upstream RCP/`esp_rcp_ota_*` handling is
   removed by patch 5).
4. Commits with `esp_ota_set_boot_partition(ota_M)` only if both parts verified.
5. On any failure: abort and report the error. Inactive slots may be left partially written; they
   are never booted.

Updates are allowed in every mode, including `RADIO_FAULT` and `SNIFFER`. One update at a time.
After a successful upload the device replies 200 and reboots.

### 5.6.1 Radio firmware update (replaces "radio sync", R14)

`POST /device/radio/firmware` (body = the `c6_rcp.bin` app image, or an empty body with the query parameter
`?from_url=<url>` to pull it from a URL) stream the image straight into the C6 updater with the existing
`BEGIN`/`DATA`/`END` protocol. Nothing is buffered beyond one 4 KB frame and nothing is stored on the
P4. The handler runs asynchronously (same pattern as OTA); one long operation (OTA or firmware push)
at a time.

1. Preconditions: mode is `BR_RUNNING` or `RADIO_FAULT` (409 in `SNIFFER` or while an OTA/firmware push
   runs); the total size is known (400 `length_required` otherwise) and fits the slot (413 `payload_too_large`,
   checked before anything is torn down; 400 `image_too_large` only when the C6's own slot check at `BEGIN`
   refuses it).
2. The BR stops (Thread and OpenThread stopped like the old resync), GPIO6 low, pulse GPIO54 → updater;
   `HELLO`; `BEGIN(size)`, `DATA`…, `END`; the C6 verifies and switches boot slot only on `END`.
3. Drive GPIO6 high, hardware-reset the C6, restart OpenThread (§5.3 step 4). The probe result is
   refreshed so `rcp.installed` shows the new version; the HTTP reply is sent when the push finished.
4. **Retry contract.** Per-frame NAK/timeout resends always apply. For the upload variant the source
   is a one-shot HTTP stream, so a failed transfer is **not** retried by the P4: it aborts cleanly
   (previous firmware intact, because only `END` switches the boot slot), restarts the BR with the
   previous firmware and replies with an error; the client re-uploads. For the URL variant the source
   can be re-opened, so up to 3 whole-transfer attempts (each from `BEGIN`) are made.
5. Errors: JSON `{error, detail}`; an image the C6 rejects at `END` (verification failed) → 400
   `invalid_image`, any other transfer or C6 failure → 502 `push_failed`; the previous firmware
   remains the boot slot.

running Thread stack or the radio (state changes, dataset writes, commissioner, ePSKc, network scan,
form/join). Read-only status endpoints keep working.

### 5.9 DHCPv6 Prefix Delegation

Compiled in by ESP-IDF (`OPENTHREAD_CONFIG_BORDER_ROUTING_DHCP6_PD_ENABLE=1`,
`..._DHCP6_PD_CLIENT_ENABLE=1`, OpenThread's native PD client). Enabled at BR start, no toggle.
When a prefix is delegated, Thread devices get global addresses; protection from the Internet then
relies on the upstream router's IPv6 firewall.

Phase 0 behaviour notes: OpenThread raises T1/T2 to at least 300 s, so a delegating router must
offer lifetimes above that (normal routers use hours); a server sending Preference 255 is preferred;
`br pd disable` releases the prefix; on lease loss the OMR falls back to the local ULA.

`/device/status` `pd.state` mirrors OpenThread's DHCPv6-PD client state (`disabled`, `stopped`, `running`; ruling R34).
The client is `running` while it solicits, so with no delegating router `pd.state` is `running` with `pd.prefix` null
and the local ULA OMR prefix is used. `idle` does not exist.

### 5.10 Maintenance jumper: ROM recovery and C6 log capture

Only active when the jumper is detected (§5.3 step 3.1). ROM recovery restores the **C6 base image**
only (R14); it does not write RCP firmware, which is not stored on the P4.

**ROM recovery** (`rcp_sync`, using `esp-serial-flasher` directly over `JUMPER_TX`/`JUMPER_RX`,
`JUMPER_BOOT` as BOOT and GPIO54 as reset). Upstream's `esp_rcp_update()` flasher is not used (and the
component is not a dependency, R14): it writes only a bootloader, a partition table and one app,
while the C6 layout needs `otadata` plus two apps.

1. Hold `JUMPER_BOOT` low, pulse GPIO54 → C6 enters ROM download; connect, verify target is
   ESP32-C6, raise baud rate.
2. Write the embedded C6 bootloader and partition table, erase `otadata`, write the embedded
   `c6_updater` to `test`; verify each write. `ota_0`/`ota_1` are left as they are (a previously
   installed RCP remains if its slot is intact; `otadata` erased means the first valid slot boots).
3. Release `JUMPER_BOOT`, reset. The C6 boots the updater-verified layout; `HELLO` follows. A C6 with
   no RCP firmware (first install, erased flash) reports an empty version → `RADIO_FAULT` reason
   `"no rcp firmware"` → the user uploads the RCP via `/device/radio/firmware` (§5.6.1).

Triggers: updater silent after retries (first install, corrupted updater/bootloader/partition
table), `updater_version` different from the embedded base image version (field update of the base
image), and `POST /device/radio/recover`. ROM recovery is attempted at most once per boot
automatically. A failed recovery is a fault only when the updater was silent before it (`RADIO_FAULT`
`"rom recovery failed"`); after a mere version mismatch the installed RCP keeps running and the failure shows as
`jumper.recovery_failed` in `/device/status`.

**C6 log capture:** outside ROM recovery, the P4 receives C6 UART0 output on `JUMPER_RX` into a
16 KB ring buffer (PSRAM), forwards complete lines to the P4 log with a `c6:` prefix, and serves the
buffer at `GET /device/radio/log`. `JUMPER_TX` stays idle.

### 5.11 Core scheduling

Goal: management bursts (OTA, sniffer streaming, large REST responses) never add latency to packets
routed between Ethernet and Thread. All application-relevant tasks are pinned.

| Core | Tasks and interrupts |
|---|---|
| **0 — network** | lwIP `tcpip`; Ethernet EMAC RX task and ISR; OpenThread task (spinel SPI, Thread stack, BR); SPI/INT ISRs of the RCP link; default `esp_event` loop; mDNS; `esp_timer` |
| **1 — management** | HTTP server and its async workers (pcap stream, OTA upload, radio firmware push); upstream `thread_rest` worker (patch 11); `device_api`; `rcp_sync` (probe, firmware push, ROM recovery); C6 log receiver; `diag` sampler; console REPL (`console_repl`); remainder of `app_main` |

- Interrupts are allocated on the core that installs them, so Ethernet, SPI and GPIO drivers are
  initialised from a core-0 task.
- Priorities keep ESP-IDF's relative order on core 0: `tcpip` > EMAC RX > OpenThread > event loop
  > mDNS. Core-1 tasks run at or below the HTTP server's default priority.
- Pinning uses ESP-IDF's own settings where they exist (`CONFIG_LWIP_TCPIP_TASK_AFFINITY`,
  `CONFIG_MDNS_TASK_AFFINITY`, `httpd_config_t.core_id`, EMAC "pin to creating core" flag) and
  `xTaskCreatePinnedToCore` for tasks we create (OpenThread task, workers, sampler). All exist in
  v6.1 (`CONFIG_LWIP_TCPIP_TASK_AFFINITY_CPU0`, `CONFIG_MDNS_TASK_AFFINITY_CPU0`,
  `ETH_MAC_FLAG_PIN_TO_CORE`, `httpd_config_t.core_id`); the default event loop is already pinned
  to core 0.
- **Flash write stalls — solved by XIP from PSRAM.** In normal XIP-from-flash mode every flash
  erase/write suspends the scheduler on both cores (Phase 0: Thread-path p99 ≈ 300 ms, max 1.3 s,
  loss). `CONFIG_SPIRAM_XIP_FROM_PSRAM=y` copies `.text`/`.rodata` to PSRAM at boot; flash and PSRAM
  are on separate MSPI buses on P4, so erase/write only takes a mutex and both cores keep running.
  Phase 0 with XIP: 64 KB-block erases without yields left Thread-path p99 at 49 ms (baseline 51 ms),
  Ethernet max 2 ms, no loss. Rules: our code never keeps a flash region mmapped without
  `SPI_FLASH_MMAP_FLAG_BLOCKS_WRITE`; no chunk/yield scheme is needed.
  Rejected alternatives: `CONFIG_SPI_FLASH_AUTO_SUSPEND` (asserts at boot for this GigaDevice flash
  in v6.1); linker fragments placing OpenThread in IRAM (scheduler is suspended anyway in flash-XIP
  mode, and OpenThread's 405 KB of text does not fit the 179 KB of executable internal RAM on
  rev < 3 silicon).
- **OpenThread lock:** upstream REST handlers run on core 1 but hold the OpenThread lock, which
  blocks the OpenThread task regardless of core. Lock hold time is measured (§5.12); if upstream
  collection endpoints (topology, diagnostics) exceed 20 ms, they are patched to copy data under the
  lock and build JSON after releasing it.
- VLAN demultiplexing (`netcfg`) runs in the EMAC RX path on core 0; the confirm timer and console
  run on core 1.
- The P4 LP core is unused in the MVP.

### 5.12 Diagnostics (`diag`)

- Build config (all builds, not only debug): `CONFIG_FREERTOS_USE_TRACE_FACILITY=y`,
  `CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS=y`.
- A sampler task on core 1 (lowest application priority) calls `uxTaskGetSystemState()` once per
  second, computes per-task runtime deltas, and maintains rolling windows of **1 s, 10 s and 60 s**
  in PSRAM. `GET /device/diag` serves the precomputed snapshot, so a request never walks the task
  list itself.
- **OpenThread lock statistics** without patching upstream: `esp_openthread_lock_acquire` /
  `esp_openthread_lock_release` are wrapped at link time (`-Wl,--wrap`) to record acquisition
  count, wait time and hold time per caller task.

`GET /device/diag` response (JSON):

| Field | Content |
|---|---|
| `uptime_s`, `reset_reason` | since boot; `esp_reset_reason()` name |
| `cpu[]` | per core: `core`, `load_pct` for `1s` / `10s` / `60s` (100 − idle share on that core) |
| `tasks[]` | per task: `name`, `core` (pinned core or `any`), `priority`, `state`, `cpu_pct` for `1s` / `10s` / `60s`, `stack_free_min_bytes` (high-water mark) |
| `memory` | internal RAM and PSRAM: `free`, `min_free`, `largest_free_block` |
| `ot_lock` | `acquisitions`, `max_hold_us`, `max_wait_us` since boot and over the last 60 s, and the task that holds it longest |

The device page shows per-core load and the task table, refreshed every 2 s.

### 5.13 Network interfaces and VLANs (`netcfg`)

**Modes**

| Mode | Interfaces | Carries |
|---|---|---|
| `single` (default) | one interface, untagged or one VLAN ID | everything: management, Thread backbone, REST |
| `split` | `mgmt` and `thread_bb`, each untagged or a VLAN ID; **at most one untagged**; IDs distinct | `mgmt`: Web UI, `/device/*`, read-only `GET /node/*`; `thread_bb`: OpenThread backbone (RA/ND, DHCPv6-PD, NAT64 IPv4 egress, Border Agent and SRP advertising proxy mDNS, multicast forwarding) and the full Thread REST API (HA) |

Both interfaces share the board's MAC address (separate broadcast domains). Untagged frames go to the
untagged interface if there is one and are dropped otherwise; tagged frames with an unknown VLAN ID
are dropped.

**Mechanism — driver-level 802.1Q (validated in Phase 0).** One Ethernet driver, at most two
`esp_netif`s. lwIP never sees VLAN headers; **no lwIP VLAN hooks** (rejected: `PBUF_LINK_HLEN` is
18 only where `LWIP_HOOK_VLAN_SET` is defined, so packets built by OpenThread's prebuilt library
lack header room for the tag and every ND/RS send on the VLAN backbone failed; the hooks also
change `struct netif` usage the prebuilt library depends on). ESP-IDF v6.1 has no esp_eth VLAN
sub-layer (only `master` does).

- An **untagged** interface uses the stock `esp_eth_new_netif_glue()`.
- A **tagged** interface uses `netcfg`'s own esp_netif driver glue: TX inserts the 4-byte tag with
  `esp_eth_transmit_vargs(eth, 3, hdr, 12, tag, 4, payload, len - 12)` (no copy); its
  `driver_free_rx_buffer` frees `buffer - 4`; `driver_set_mac_filter` forwards to
  `ETH_CMD_ADD/DEL_MAC_FILTER`; `netcfg` drives it from `ETH_EVENT`s
  (`esp_netif_action_start/connected/disconnected`).
- RX demux is installed with `esp_eth_update_input_path_info()` **after** all attaches (the stock
  glue installs its own in `post_attach`): matching VLAN ID → move the MAC header 4 bytes forward
  and `esp_netif_receive(netif, buf + 4, len - 4)`; untagged → the untagged interface (dropped if
  none); unknown VLAN ID → free and count.
- `single` mode with a VLAN ID uses the tagged glue for its only interface.

**Isolation rules (split mode)**

1. **No forwarding between VLANs.** A packet is never forwarded if its input or output interface is
   `mgmt`; `mgmt` only carries traffic to/from the device itself. IPv6: the prebuilt
   `libopenthread_br.a` defines both `lwip_hook_ip6_input` and `lwip_hook_ip6_route` (strong
   symbols replacing IDF's weak defaults), so `netcfg` chains them with
   `-Wl,--wrap=lwip_hook_ip6_input -Wl,--wrap=lwip_hook_ip6_route`, declared as INTERFACE link
   options of the `netcfg` component (validated in Phase 0). The input wrapper drops non-local
   packets arriving on `mgmt` and non-local packets whose route resolves to `mgmt`, then calls the
   original hook. IPv4
   forwarding stays disabled (`CONFIG_LWIP_IP_FORWARD=n`); NAT64 egress is generated locally by
   OpenThread's translator.
2. **Replies leave by the interface they belong to.** Source-based routing: a packet whose source
   address belongs to `mgmt` is sent via `mgmt`. IPv4: already done by ESP-IDF's built-in
   `ip4_route_src_hook` (routes via the netif owning the source address) — no custom hook. IPv6:
   the `lwip_hook_ip6_route` wrapper returns the `mgmt` netif for `mgmt` source addresses and
   otherwise calls the original. The default interface is the backbone (NAT64 needs it).
3. **Services on their side only.** `netcfg_request_allowed(req, service)` maps the request's local
   address (`httpd_req_to_sockfd` + `getsockname`; IPv4 arrives as `::FFFF:a.b.c.d` on the
   dual-stack socket — validated in Phase 0) to an interface and applies the policy table
   above; refused requests get 403 and the connection is closed. Requests addressed to the
   OpenThread interface count as `thread_bb`. mDNS: single mode as before; split mode on
   `thread_bb` only (hostname and every service), never on `mgmt`.
4. **Multicast.** Both interfaces register their IPv6 multicast groups through
   `driver_set_mac_filter`; Phase 0 confirmed RA/RIO, ND and SLAAC on a tagged interface.

**Configuration** (`netcfg` NVS namespace `otbr_net`), JSON shape used by `/device/network`:

```
{ "mode": "single" | "split",
  "single":    { "vlan": 0 | 1..4094, "ipv4": { "dhcp": true } | { "dhcp": false, "addr", "mask", "gw", "dns" } },
  "mgmt":      { same shape as "single" },          # split only
  "thread_bb": { same shape as "single" } }         # split only
```

`vlan: 0` means untagged. Build-time defaults (`p4/main/board.h`-adjacent constants, not Kconfig):
`single`, untagged, DHCPv4. Validation: VLAN IDs 1..4094, distinct in split mode, at most one
untagged, static IPv4 fields well-formed and mask contiguous.

**Apply with confirm-or-revert:**

1. `PUT /device/network` validates, stores the config as **pending trial**, and reboots.
2. On boot with a pending trial, the trial config is used and a 5-minute confirm timer starts.
3. `POST /device/network/confirm`, received on the trial's management interface (the single
   interface in `single` mode), commits it: trial becomes active, timer stops.
4. If the timer expires (or the device resets before confirming), the trial is discarded and the
   device reboots into the previous active config. A trial survives exactly one boot.

**Implementation notes (Task 19):**

- `eth_driver_start()` only installs the Ethernet driver; `netcfg_start()` creates the netifs, registers the event handlers and
  then starts the driver (a driver started earlier would lose the link-up events the netifs need).
- The HTTP server (started early by `app_main`) listens on any address; it decides per request, by the local address of the
  request's socket, so interfaces that appear later are served as soon as they have an address. Before `netcfg_start` creates a
  split config every request is allowed (no interface exists, so none arrives).
- A request addressed to an address of the other interface is cut off in IPv6 by the input hook (strict host model: a packet
  arriving on `mgmt` for any address but mgmt's own, or on another interface for a `mgmt` address, is dropped). IPv4 has no such
  hook in lwIP's configuration (CONFIG_LWIP_IP_FORWARD=n only stops forwarding): lwIP accepts an IPv4 packet for any local
  address, so a host that forces its frames to the board's MAC with the other interface's IPv4 address as destination is
  classified by that address (a known residual gap of IPv4, needs a deliberately misrouted frame inside the segment).
- mDNS (R31, Task 19B): `netcfg` registers with `mdns_register_netif` only the interface for which `netcfg_mdns_allowed` is true:
  the single interface in single mode, `thread_bb` in split mode. `mgmt` is never registered: no announcements (hostname and
  every service, `_meshcop._udp` included), no answers, no joins of the mDNS multicast groups, and the library drops datagrams
  that arrive on an unregistered netif; `mdns_netif_action` is never called for it. Boot log: `mDNS active on <iface>` /
  `mDNS not on mgmt`. Behind a gateway that reflects mDNS between the two VLANs the `thread_bb` announcement is also seen on the
  `mgmt` VLAN, with `thread_bb`'s source and addresses; that is the reflector, not the board. Own-announcement rule: a received
  mDNS datagram whose source is an address of another interface of the board (IPv4, IPv6 incl. link-local, IPv4-mapped) and not
  of the interface it arrived on is dropped before the library (`mdns_filter.c`, `--wrap=udp_recv`, PATCHES.md 13), so the host
  never renames itself (`esp-otbr-xxxxxx-N`) on a reflected rig. The filter does not drop shared link-local sources: both VLAN
  netifs have the identical EUI-64 link-local address, which is an address of the input netif too; the library's own-source check
  (link-local and IPv4 address of the input netif) suppresses those, so `CONFIG_MDNS_SKIP_SUPPRESSING_OWN_QUERIES` must stay
  unset (guarded by `tools/tests/test_mdns_config.py`). The same-interface case is the normal loopback of our own multicast and is
  left to the library. Hardware check: V3b (`test_vlan.py`).
- IPv6 route hook (split mode): a mgmt source leaves via mgmt; no other source ever resolves to mgmt (when the original hook
  says mgmt, or says nothing and no other interface has the destination on-link, the backbone is returned, so lwIP never falls
  back to a default router learned on mgmt).
- Failure handling: the storage-only calls (`net reset`, PUT/confirm, state) work before any interface exists. A stored active
  config that cannot be applied is replaced by the defaults in the same boot (`fallback: true` and `error` in
  `GET /device/network`); a trial that cannot be applied is discarded and the board reboots into the previous config.
- Frames of an unknown VLAN ID, untagged frames without an untagged interface and malformed tags are dropped and counted
  (`vlan_rx_dropped` in `GET /device/network`).

**Recovery:** the P4 console (USB-C UART) offers `net show` and `net reset` in all builds;
`net reset` restores the build-time defaults and reboots.

## 6. Error handling summary

| Situation | Behaviour |
|---|---|
| Boot probe fails (no HELLO answer) with a working C6 boot slot | boot continues; installed version "unknown"; OpenThread's compatibility check decides |
| No valid RCP firmware installed (empty version) | `RADIO_FAULT` reason `"no rcp firmware"`; Web UI up; upload RCP via `/device/radio/firmware` |
| OpenThread rejects the installed RCP | `RADIO_FAULT` reason `"rcp incompatible"`; upload compatible firmware |
| Radio firmware push fails (C6 reset, NAK exhaustion, verify error) | abort; previous firmware stays the boot slot; BR restarts; JSON error; upload: client re-uploads; URL: up to 3 attempts |
| C6 updater silent (corrupt updater/bootloader/partition table, or first install) | with jumper: ROM recovery (base image), then upload RCP; without jumper: `RADIO_FAULT`, H7 + USB-UART needed |
| ROM recovery fails (no sync, wrong chip, write/verify error) | updater was silent: `RADIO_FAULT` `"rom recovery failed"`; updater was reachable (base version mismatch only): the boot continues with the installed RCP and `/device/status` `jumper.recovery_failed` is `true`. Either way no further automatic attempt this boot |
| RCP failure at runtime | recovery ladder (§5.4), rate-limited |
| OTA failure | abort, error reply; running pair untouched |
| OTA requested while the running image is pending verification (first 60 s) | 409 `busy`, "retry in up to 60 s"; nothing erased (the inactive web slot is the rollback target's) |
| NVS does not initialise (no free pages, corrupt) | degraded boot instead of a boot loop: HTTP, OTA, `/device/*` run, `storage_ok` false, OpenThread not started (`RADIO_FAULT` `"storage unavailable"`); NVS is never erased automatically (Thread credentials) |
| OpenThread reports an RCP failure inside a task other than its own (httpd, REST worker, capture stream) | `RADIO_FAULT` is recorded and the device reboots; the task is never deleted |
| New P4 image crashes / hangs / brownout before validity | bootloader rollback to previous pair |
| New P4 image boots but radio/Ethernet issues | no rollback; recovery via OTA (allowed in all modes) |
| Sniffer ring overflow | drop and count |
| Sniffer client gone / stream error | stop capture, return to BR |
| BR restore after sniffing fails | reboot |
| Task watchdog / panic | coredump to `coredump` partition, reboot |
| New network config unreachable / not confirmed within 5 min | discard trial, reboot into previous config |
| Invalid network config submitted | 400 with the failing field; nothing stored |
| Locked out by a confirmed but wrong network config | `net reset` on the USB console restores defaults |
| Request on the wrong interface (split mode) | 403 and connection closed |

## 7. Styleguide

There is no existing styleguide; the implementation plan's first step creates `STYLEGUIDE.md` with:

- **C formatting:** ESP-IDF's astyle rules, enforced via `pre-commit` (`astyle_py`, same config as
  ESP-IDF). Vendored upstream code is excluded to keep diffs small.
- **Python (tools, pytest):** `ruff` format + lint.
- **Naming:** `snake_case`; public symbols prefixed with their component name (`br_core_`,
  `rcp_sync_`, `sniffer_`, `device_api_`, `diag_`, `netcfg_`, `rcp_sync_proto_`); one `static const char *TAG` per file
  named after the component.
- **Errors:** functions return `esp_err_t`; propagate with `ESP_RETURN_ON_ERROR` /
  `ESP_GOTO_ON_ERROR`; `ESP_ERROR_CHECK` only for unrecoverable init in `app_main`.
- **Config:** fixed hardware facts are constants in headers, not Kconfig.
- **Tests:** host tests in `<component>/test_host/` using Unity on the ESP-IDF `linux` target,
  `TEST_CASE("<scenario>: <effect>", "[<component>]")`; target tests in `p4/pytest/test_<feature>.py`
  with `pytest-embedded`.

## 8. Behaviour contract (BDD skeleton)

```
rcp_sync_proto (common)
    frame encode/decode
        On valid frame
            - decodes type, seq and payload identical to the encoded input
        On CRC mismatch
            - returns ESP_ERR_INVALID_CRC
        On payload length > 4096
            - returns ESP_ERR_INVALID_SIZE

c6_updater
    HELLO
        On boot slot with verifiable image
            - replies boot_slot_version equal to that image's PROJECT_VER
        On boot slot empty or unverifiable
            - replies empty boot_slot_version
    BEGIN
        On image_size within slot size
            - erases the inactive slot
            - replies OK
        On image_size larger than slot size
            - replies ERR(size)
    DATA
        On offset equal to next expected offset
            - writes bytes to the inactive slot
            - replies OK(next_offset)
        On unexpected offset
            - replies ERR(expected_offset) and writes nothing
        On repeated seq
            - replies the cached reply without writing
    END
        On image that verifies
            - sets boot slot to the written slot
            - replies OK
        On image that fails verification
            - leaves boot slot unchanged
            - replies ERR(verify)
    any request
        On CRC mismatch
            - replies NAK

rcp_sync (P4)
    rcp_sync_probe
        On updater answering HELLO with a boot-slot version
            - returns that version as the installed version
            - sends no BEGIN
        On updater answering HELLO with an empty boot-slot version
            - returns an empty installed version
        On updater not answering after the normal retries
            - returns an error and no version
        On completion (any result)
            - releases the SPI bus
            - drives GPIO6 high
            - JUMPER_BOOT is high-impedance
    rcp_sync_push_firmware
        On source of valid size and a healthy transfer
            - sends BEGIN with the total size, DATA in sequential offsets and END once
            - returns OK
        On a frame NAK or timeout
            - resends the same seq and completes the transfer
        On source with size 0 or larger than slot_size
            - sends no BEGIN
            - returns an invalid-image error
        On C6 reset mid-transfer with a one-shot source (upload)
            - makes no whole-transfer retry
            - returns a transfer error
            - the previous firmware remains the boot slot (no END was sent)
        On C6 reset mid-transfer with a re-openable source (URL)
            - retries the whole transfer from BEGIN, up to 3 attempts
            - returns OK if an attempt completes, else a transfer error
        On END replying ERR(verify)
            - returns a verify error
            - the previous firmware remains the boot slot
        On completion (any result)
            - releases the SPI bus
            - drives GPIO6 high
            - JUMPER_BOOT is high-impedance
    jumper detection
        On C6 ROM boot banner received on JUMPER_RX during reset
            - reports jumper present
        On no bytes received during reset
            - reports jumper absent
            - never drives JUMPER_TX or JUMPER_BOOT
    ROM recovery
        On jumper present and updater silent after retries
            - writes bootloader, partition table and updater
            - writes no RCP firmware
            - erases otadata
            - C6 answers HELLO with the embedded base image version afterwards
        On jumper present and updater_version differs from embedded base version
            - performs ROM recovery once
        On jumper absent
            - is not attempted
        On second trigger within the same boot (automatic)
            - is not attempted
        On target chip not ESP32-C6 or write verification failure
            - returns error and leaves JUMPER_BOOT high-impedance
    C6 log capture
        On C6 console output while not in ROM recovery
            - appends to the 16 KB log ring buffer
            - forwards complete lines to the P4 log prefixed "c6:"

br_core
    boot
        On stored active dataset and Ethernet address
            - starts Thread with the stored dataset
            - enables DHCPv6-PD
            - enters BR_RUNNING
        On no stored dataset
            - does not form a network
            - enters BR_RUNNING (idle)
        On probe reporting an empty installed version
            - does not start OpenThread
            - enters RADIO_FAULT with reason "no rcp firmware"
            - HTTP server is still started
        On OpenThread failing to initialise the RCP
            - enters RADIO_FAULT with reason "rcp incompatible"
            - status rcp.compatible is false
            - HTTP server is still started
        On probe failing but OpenThread accepting the RCP
            - enters BR_RUNNING
            - status rcp.installed is null
        On probe returning a version
            - status rcp.installed equals that version
            - status rcp.compatible is true after OpenThread started
    radio firmware push
        On a push request in BR_RUNNING or RADIO_FAULT
            - stops OpenThread, pushes, hardware-resets the C6 and restarts OpenThread
            - refreshes status rcp.installed
        On a push request in SNIFFER or while another long operation runs
            - returns an invalid-state error and starts nothing
        On push failure
            - restarts OpenThread with the previous firmware
    app validity
        On pending-verify image, HTTP server listening, 60 s uptime
            - marks the app valid
        On pending-verify image in RADIO_FAULT or without Ethernet link
            - still marks the app valid after 60 s
    mode: enter sniffer
        On BR_RUNNING and valid channel
            - disables Thread and the OpenThread netif
            - enables the raw link before setting channel and promiscuous mode
            - enables raw link in promiscuous mode on the channel
            - Ethernet addresses remain configured
            - enters SNIFFER
        On mode other than BR_RUNNING
            - returns ESP_ERR_INVALID_STATE
    mode: leave sniffer
        On stop request
            - restores the dataset channel and restarts Thread
            - active dataset TLVs are identical to those before entering SNIFFER
            - enters BR_RUNNING
        On restore failure
            - reboots
    radio fault recovery
        On RCP failure callback
            - resets the C6 and restarts OpenThread
            - enters BR_RUNNING on success
        On 4th failure within 10 minutes
            - stays in RADIO_FAULT without automatic recovery
    br_core_thread_ops_allowed
        On BR_RUNNING
            - returns true
        On SNIFFER or RADIO_FAULT
            - returns false

sniffer
    capture
        On frame received
            - appends a pcap record with channel, RSSI, LQI TLVs and timestamp
        On ring buffer full
            - drops the frame and increments the drop counter
    stream
        On client connect
            - writes a pcap global header with link type 283
        On client disconnect, duration elapsed or DELETE /device/sniffer
            - stops capture and requests BR mode

esp_br_http_ota (patched core)
    bundle
        On valid bundle
            - writes web_M and ota_M
            - sets boot partition to ota_M
        On web SHA-256 mismatch
            - aborts without changing the boot partition
        On invalid P4 image
            - aborts without changing the boot partition
        On second concurrent update
            - rejects with 409

device_api
    GET /device/status
        On any mode
            - returns 200 with mode, versions, rcp {installed, compatible}, PD state, sniffer stats
    GET /device/sniffer.pcap
        On BR_RUNNING
            - streams pcap until stopped
        On SNIFFER or RADIO_FAULT
            - returns 409
        On channel outside 11..26 or duration > 3600
            - returns 400
    POST /device/ota
        On valid bundle
            - returns 200 and reboots into the new slot
        On invalid bundle
            - returns 400 and keeps running
    POST /device/radio/firmware
        On BR_RUNNING or RADIO_FAULT and a valid c6_rcp.bin body
            - streams it to the C6 without storing it on the P4
            - restarts OpenThread and returns 200
        On invalid image or unknown body size
            - returns 400 and keeps the previous firmware
        On C6 reset mid-transfer
            - returns a JSON error {error, detail}
            - the previous firmware still boots
        On SNIFFER or OTA/firmware push in progress
            - returns 409
    POST /device/radio/firmware?from_url=<url>
        On reachable URL with a valid image
            - behaves like POST /device/radio/firmware
        On transfer failure
            - retries the whole transfer up to 3 times
        On unreachable URL
            - returns a JSON error and keeps the previous firmware
        On SNIFFER or OTA/firmware push in progress
            - returns 409
    POST /device/radio/recover
        On jumper present and BR_RUNNING or RADIO_FAULT
            - performs ROM recovery of the base image and restarts OpenThread
            - does not write RCP firmware
        On jumper absent
            - returns 412
        On SNIFFER or update in progress
            - returns 409
    GET /device/radio/log
        On jumper present
            - returns the captured C6 console text
        On jumper absent
            - returns 412
    GET /device/diag
        On any mode
            - returns 200 with cpu, tasks, memory and ot_lock sections
            - does not call uxTaskGetSystemState in the request path

netcfg
    config validation
        On split mode with two untagged interfaces
            - rejects with field "vlan"
        On split mode with equal VLAN IDs
            - rejects with field "vlan"
        On VLAN ID 0 (untagged) or 1..4094
            - accepts
        On VLAN ID 4095 or above
            - rejects with field "vlan"
        On static IPv4 with non-contiguous mask
            - rejects with field "ipv4.mask"
    interfaces
        On single mode untagged
            - one interface receives untagged frames
        On split mode
            - mgmt and thread_bb receive only frames with their VLAN ID (or untagged for the untagged one)
            - frames with an unknown VLAN ID are dropped
        On split mode
            - the OpenThread backbone netif is thread_bb
    isolation (split mode)
        On packet arriving on mgmt not addressed to the device
            - is dropped, not forwarded
        On packet from thread_bb or Thread whose route resolves to mgmt
            - is dropped, not forwarded
        On reply to an off-subnet management client
            - leaves via mgmt
    request policy (split mode)
        On /device/* or Web GUI request arriving on mgmt
            - is allowed
        On /device/* or Web GUI request arriving on thread_bb
            - returns 403 and closes the connection
        On PUT /node/dataset/active arriving on mgmt
            - returns 403
        On GET /node/state arriving on mgmt
            - is allowed
        On any /node/* or /api/* request arriving on thread_bb
            - is allowed
    request policy (single mode)
        On any request
            - is allowed
    confirm-or-revert
        On PUT /device/network with valid config
            - stores it as pending trial and reboots into it
        On POST /device/network/confirm on the trial's management interface within 5 min
            - makes the trial the active config
        On no confirm within 5 min
            - reboots into the previous active config
        On reset during the trial
            - next boot uses the previous active config
        On console "net reset"
            - restores defaults (single, untagged, DHCPv4) and reboots

diag
    sampler
        On each 1 s tick
            - updates per-task cpu_pct for the 1 s, 10 s and 60 s windows
            - per-core load_pct equals 100 minus that core's idle-task share
        On task created since the previous tick
            - includes it with cpu_pct computed from its runtime since creation
        On task deleted since the previous tick
            - removes it from the snapshot
    OpenThread lock wrapper
        On acquire followed by release
            - increments acquisitions
            - updates max_hold_us when the hold time exceeds the previous maximum
        On acquire that waits
            - updates max_wait_us

scheduling
    startup
        On system started
            - tcpip, EMAC RX, OpenThread, event loop and mDNS tasks report core 0
            - HTTP server, workers, rcp_sync, log receiver and sampler report core 1

REST guard (esp_ot_br_server patch)
    Thread-dependent endpoint
        On SNIFFER
            - returns 409
        On RADIO_FAULT
            - returns 503
    read-only status endpoint
        On any mode
            - returns 200
```

## 9. Testing strategy

- **Host (Linux target, Unity):** `rcp_sync_proto`; `c6_updater` request handling against a fake
  flash; bundle-header parsing and 0xFF trimming; `br_core` mode state machine with OpenThread
  stubbed; upstream `esp_ot_br_server` host tests (`run_host_tests.py`) kept green after patches.
- **Target (`pytest-embedded`, real board):**
  - radio firmware upload: fresh C6 (no RCP → `RADIO_FAULT` "no rcp firmware" → upload → BR), upload of
    a different version (both directions), C6 reset injected mid-transfer (clean failure, previous
    firmware still boots, retry succeeds), invalid image, URL variant;
  - OTA: upload → reboot → correct `(ota, web)` pairing; crashing image → rollback; HTTP client
    disconnect mid-upload leaves the running pair untouched;
  - sniffer: 20 start/stop/disconnect cycles, BR healthy after each;
  - maintenance jumper (run with and without the jumper fitted): detection; first install onto a C6
    with factory ESP-Hosted firmware; recovery after erasing the C6 `test` partition and after
    erasing the C6 bootloader; base image version bump triggers exactly one recovery; C6 log
    endpoint;
  - HA compatibility: `tools/` script driving `python-otbr-api` against the board (dataset get/set,
    channel change via pending dataset, factory reset, ePSKc, coprocessor version);
  - **latency isolation:** continuous ping from the LAN to a Thread device during (a) an OTA upload or an RCP firmware push,
    (b) a pcap stream, (c) repeated topology requests; pass = no loss and p99 added latency
    < 50 ms over the idle baseline; `/device/diag` captured alongside;
  - scheduling: `/device/diag` reports every task on its specified core;
  - RCP link start: 5 P4 resets and the first boot after a P4 flash each reach an attached BR with
    no SPI timeouts and no assert (failure handler registered);
  - sniffer channel switching leaves the active dataset byte-identical (20 cycles);
  - test hosts on the board's segments are Docker `macvlan` containers on the host's existing VLAN
    interfaces (IPv6 only, Docker address range inside the VLAN's ULA, `accept_ra=2`,
    `accept_ra_rt_info_max_plen=64`) — no host network changes;
  - VLANs (managed switch with a trunk port to the board): single untagged and single tagged;
    split with tagged/tagged and untagged/tagged; no forwarding between VLANs (probe from each side
    to a host on the other); per-interface policy; HA REST reachable on `thread_bb` only; confirm
    and revert paths; `net reset`.
- **Host:** `netcfg` config validation and policy table.
- **Host:** `diag` window arithmetic (runtime deltas, counter wrap, task appear/disappear) with a
  fake task list.

## 11. Risks

| Risk | Mitigation |
|---|---|
| SPI spinel on C6 less exercised than UART | validated in Phase 0 (10–40 MHz, 5/5 starts); spinel-over-SPI has no CRC → 10 MHz margin; fallback: UART spinel over the jumper wires |
| Vendored esp-thread-br code is unreleased `main` | pinned commit, `PATCHES.md`, upstream host tests kept running |
| User runs an RCP the P4 build does not understand (RCP is versioned independently) | OpenThread's compatibility check at boot → `RADIO_FAULT` "rcp incompatible"; status shows installed version; documented release pairing in README |
| RCP upload interrupted (HTTP client gone, C6 reset) | only `END` switches the boot slot → previous firmware keeps booting; client re-uploads; target test with injected reset |
| First install leaves the C6 without RCP firmware | expected: `RADIO_FAULT` "no rcp firmware" until the user uploads `c6_rcp.bin`; documented first-install step |
| No authentication | documented non-goal; LAN must be trusted |
| Delegated prefix makes Thread devices globally addressable | relies on upstream router firewall; documented |
| Frozen C6 updater / bootloader bug | small scope, host + target tests; recoverable via maintenance jumper (ROM recovery) or H7 + USB-UART |
| Flash erase/write stalls both cores during OTA | XIP from PSRAM (validated); no mmapped flash without `BLOCKS_WRITE`; latency-isolation test covers OTA |
| Upstream handlers hold the OpenThread lock too long | lock wrapper metrics; patch offending handlers if > 20 ms |
| lwIP hook conflicts with the OpenThread port's hooks | link-time `--wrap` of both IPv6 hooks (validated); no lwIP VLAN hooks at all |
| Prebuilt `libopenthread_br.a` depends on `struct netif` layout | never change lwIP options affecting `struct netif`; boot test asserts no "Invalid If index" |
| PSRAM-XIP side effects (boot time, PSRAM usage) | ~1.5 MB PSRAM, ~150 ms boot; measured in Task 18 |
| Network misconfiguration locks the user out | confirm-or-revert trial; `net reset` on USB console |
| Accidental routing between management and Thread VLANs | forwarding filter + dedicated isolation tests |
| User's router does not delegate prefixes | PD verified against our own server; fall back to ULA OMR automatically; document router requirements |
| Jumper wiring mistake drives a C6 strap pin at boot | `JUMPER_BOOT`/`JUMPER_TX` high-impedance by default; driven only inside ROM recovery |
